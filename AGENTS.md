# PACU project rules

This is Trevor Kazahaya's independently owned personal project for Pacific Baseball players and coaches. It is not an official university application. Preserve existing work and keep changes within the explicitly requested phase.

- Stack: Next.js App Router, TypeScript, Tailwind, Supabase Auth/PostgreSQL, Vercel. Use the lockfile and current official documentation.
- The owner now requires sign-in for every dashboard route. The home route leads to the branded sign-in screen or the authorized team workspace. `/preview` is an Admin-only browser import/review workspace behind live trusted authorization, unavailable during the private Coach/Player View as mode. Its IndexedDB data stays local; access checks use Supabase but report processing does not upload files, create sessions or grant roles. A separate, explicitly approved private measurement-sharing workflow uploads only whitelisted numeric observations and provenance.
- No public signup, demo account, anonymous database roster reads, authentication bypass for protected routes, first-login admin, or shared/default passwords. Real roster and administrative actions require existing Auth/RLS checks.
- Normal app data access uses only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` plus the signed-in user's session. Never use a service-role/secret key for ordinary database reads or writes. The owner-requested invitation feature has one separate, server-only `SUPABASE_AUTH_ADMIN_SECRET` client, restricted to Auth directory lookup and `inviteUserByEmail`; it never reads/writes application tables. Keep `PACU_INVITATIONS_ENABLED=false` until SMTP, templates and the invitation migration are verified. Never prefix that secret with `NEXT_PUBLIC_`, serialize it, log it, or commit it.
- Authentication is separate from authorization. Check live trusted active status and database roles in every server entry point; enforce data access with RLS. Do not trust user metadata, email, UI switches, or client-supplied roles.
- Accounts and athlete identities remain separate. Only an explicitly authorized administrator/owner may set an account link. Roster emails never provision accounts or link them.
- Invitation sends require an active administrator outside preview, an individually reviewed email/Coach-or-Player role/exact athlete selection, and a fresh check before sending. Configure the returned Auth UUID through the ordinary user-session `admin_provision_invited_account` RPC, which locks and refuses existing accounts. Do not automatically resend uncertain deliveries, overwrite existing roles/links, or infer identity from email. Invitation acceptance verifies only `invite` or `recovery` after an explicit POST and never grants roles. Browser-local data does not become shared by creating logins.
- Athlete UUIDs are permanent. The owner explicitly requested a one-time migration of LOCAL-NNNN codes to PAC-NNNN with the same suffix; preserve UUIDs, measurements and account links, retain checked legacy aliases, and do not renumber on subsequent imports. Seasonal roster details live in `athlete_seasons`; performance measurements do not belong in roster fields.
- The protected Supabase roster importer accepts only its documented CSV template and matches permanent code. The browser-local Import Center accepts explicitly mapped CSV/TSV/XLSX; local roster rows may match a unique email or get a new local code. Preserve jersey `0`, merge only nonblank values, never delete omitted athletes, review all rows, and save atomically after a revision check. Measurement imports require explicit identity, dates, metrics, and units; retain source row/file provenance.
- Private SECURITY DEFINER functions must pin `search_path`, schema-qualify objects, revoke default execution, check current authorization, and keep consistent advisory-lock order. Keep the `private` schema out of exposed API schemas.
- No real roster data, production exports, credentials, access tokens, SQL dumps, or passwords in source, prompts, logs, screenshots, fixtures, or commits. Use only marked fictional `example.com` fixtures.
- The current owner-requested scope includes shared player profiles, canonical numerical imports, team account preparation and deployment. Preserve the session's explicit authorization for that work. Provisioning Auth accounts, sending emails and changing DNS remain separate actions requiring their own authorization; preparing a coach or deploying code is not email-send approval. The owner has explicitly said not yet to team emails; keep sending disabled and unsent until new explicit approval. Local checks are permitted.
- The owner expanded Phase 1 to the browser-local Import Center, then explicitly requested a RENPHO reader and supplied one private portrait Body Composition Analysis Report image. PNG/JPG and one-page PDF processing for that layout may use browser-local OCR; other vendor labels remain source tags. Do not invent additional schemas/units or claim untested layouts are supported. Known region boundaries isolate actual measurements from ranges, classifications, targets and charts. Explicit report title/ID/date/composition anchors gate layout unit conventions. Require comparison with the original before applying; no external OCR uploads or health interpretation.
- Local optional `renpho_id` and manually confirmed `renpho_ids` may propose an athlete only by unique normalized exact match. New IDs require explicit player selection. Never infer identity from names, prefixes, report dates or email, or create Auth links. Save an approved ID mapping and its measurement batch atomically with the current IndexedDB revision. Keep report images/text and unconfirmed identity evidence out of persisted measurements, backups, fixtures, source and logs. Preserve fixed metric columns/page/source lines so deselecting metrics cannot renumber deduplication IDs.
- Shared performance observations use the ordinary active-admin session and `admin_import_performance`, with bounded reviewed rows, permanent-code matching, immutable source observation IDs and atomic conflict rejection. Serialize only the exact Measurement fields from a backup; never forward unknown properties, OCR text, report images, RENPHO IDs or the complete backup. Players read only their linked observations; coach/admin reads and fixed-cohort aggregate comparisons remain protected by live access checks. Preview queries also apply the effective athlete restriction.
- Profile baseball metrics use Fall 2026 (September 1–December 31); body metrics also retain a separate June–August 2026 comparison period. Visible profiles use Last Tested with the actual date and do not label readings summer baselines. Percentiles require at least five measured athletes in the explicit 2026–27 cohort with status null/active/redshirt and the same metric, source/protocol, unit and period. Neutral body/spin ranks are numerical positions, not health or performance advice. Never infer strikeout percentage from the Pitching sheet's mislabeled K% column, which represents strike percentage. See `docs/PLAYER_PROFILES.md`.
- Coach preparation stores reviewed names/emails only; it never creates Auth users, changes roles/links or sends invitations. Direct Google Sheets-to-dashboard sync, additional unverified vendor layouts, force plates, AI interpretation and training advice remain deferred. The owner requested Pacific Baseball logo/branding. Use verified official source assets with preserved proportions and retain the independent-project disclosure. The sign-in landing quote is “People Lie, Numbers Don’t.”
- Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` after substantive changes. Browser suite: `pnpm test:ui`. Report skipped integration tests honestly; PGlite is not the full Supabase Auth/API stack.
- Keep README and `docs/SETUP.md`, `docs/DATA_MODEL.md`, `docs/TESTING.md` aligned with code.
